### Reference local run

The run from **2 August 2026 at 16:18** recorded 972 passing PHPUnit tests, 15 skipped tests, 285 passing Vitest tests, and one PHPStan L8 finding. This is a historical diagnostic snapshot, not a permanent guarantee of future counts.

### Two-stage evaluation

```text
automated result of the 21 steps
→ manual review of the complete log
→ PASS / PASS_WITH_REVIEW / INVESTIGATION_REQUIRED / FAILED
```

Manual review also checks warnings, count changes, unexplained skips, dependency findings, unexpected network requests, build warnings, and other anomalies even when the tool exits with code 0.

### Local logs and GitHub CI

- The full local log is written to `${PAGINIUMCMS_TEST_LOG_DIR:-$HOME/projects/paginiumcms_tests}/alltests_*.log`, outside the repository by default.
- A local raw log may contain diagnostic values generated by tests; it must not be committed or shared before sanitization.
- GitHub Actions uses `.github/scripts/run-backend-tests-ci.sh`, which captures raw output in runner-temporary storage, then runs `sanitize-ci-log.py` and the fail-closed `verify-ci-log-redaction.sh`.
- A GitHub job log or artifact must never contain a raw TOTP seed, QR payload, `otpauth://` URI, OTP code, bearer token, cookie, or secret.
- Raw CI output is not published and is not piped through `tee` into the public console.

Before sharing a local log:

```bash
RAW="$HOME/projects/paginiumcms_tests/alltests_DDMMYY_HHMM.log"
SAFE="${RAW%.log}.sanitized.log"
python3 .github/scripts/sanitize-ci-log.py "$RAW" > "$SAFE"
.github/scripts/verify-ci-log-redaction.sh "$SAFE"
```

Maintainer template: [`../../LOCAL_TEST_LOGS.md.example`](../../../LOCAL_TEST_LOGS.md.example). Incident and implemented fix: [ISS-120](../ISSUES.md#iss-120).

> This document is a living contract for the **`v2.1.0-beta.*`** release family. Exact test counts, CI job names, and helper-script step counts belong to a specific tag. They are not immutable architectural properties.

## 1. Test strategy objective

Testing PaginiumCMS must prove more than individual methods returning expected values. It must protect the project's primary invariants:

- flat-file documents remain the authoritative source of truth,
- writes are atomic and conflicts are never overwritten silently,
- indexes, caches, Git publishing, translations, and AI output are derived or asynchronous layers,
- authentication, authorization, Path ACL, CSRF, and 2FA are enforced by the backend,
- user input, uploads, archives, outbound URLs, and extension code pass the relevant security gate,
- tests do not mutate production data or production settings,
- a release is reproducible from a clean clone,
- upgrade, backup, restore, and rollback are verifiable operations rather than promises in a guide.

A green unit test proves one small property. A green release gate is a set of evidence about the whole candidate.

## 2. Source of truth for test commands

Historical documentation described the same `run-all-tests.zsh` runner as both an 11-step and a 21-step procedure. Such counts naturally change as the suite grows. Therefore:

1. the script in the inspected commit/tag is authoritative,
2. CI must use the same lockfiles and supported runtime matrix,
3. reports should list category names, result, duration, and build identity,
4. documentation must not guarantee a step count without tying it to a release snapshot.

Recommended discovery procedure:

```bash
./scripts/iteration-gate.sh --help 2>/dev/null || true
./scripts/run-all-tests.zsh --help 2>/dev/null || true
grep -nE 'TOTAL_STEPS|run_step|composer |npm run|phpunit|phpstan' \
  scripts/iteration-gate.sh scripts/run-all-tests.zsh
```

When a script has no `--help`, its content and the CI workflow in that tag are the source of truth. A number copied from a README three releases ago is not—documentation occasionally needs a unit test too. 🙂

## 3. Test pyramid

| Layer | Purpose | Typical dependencies | Expected speed |
|---|---|---|---|
| static checks | syntax, types, architectural rules, and forbidden patterns | source tree | seconds to minutes |
| unit tests | isolated service or policy contract | temp filesystem, mock/fake | fast |
| integration tests | repository, storage, middleware, and controller collaboration | real bootstrap, isolated storage | medium |
| HTTP contract tests | status, envelope, headers, auth, and conflicts | test app + session | medium |
| frontend component tests | UI states, forms, guards, and accessibility | jsdom, MSW | fast to medium |
| end-to-end smoke | critical user flow through the built application | running stack | slower |
| recovery tests | backup, restore, rebuild, upgrade, and rollback | disposable environment | slow |
| security regressions | exploitable boundaries and previous incidents | multiple layers | scenario-dependent |

The pyramid does not mean that a larger number of tests automatically provides higher quality. Correctly selected contracts and independent environments matter more.

## 4. Required gate levels

### 4.1 Fast local gate

Run after a small change and before committing:

```bash
./scripts/iteration-gate.sh
```

It should cover at least:

- syntax of changed PHP files,
- PHPStan on the affected scope or all of `backend/app`,
- relevant PHPUnit tests,
- TypeScript type-check,
- ESLint,
- API barrel/wiring integrity,
- forbidden extension-pattern checks when that surface changes.

The fast gate must not pretend to replace a production build, dependency audit, restore test, or full regression suite.

### 4.2 Full local gate

Use before a major merge, release candidate, or changes to storage, auth, extensions, or the publish pipeline:

```bash
./scripts/run-all-tests.zsh
```

Expected categories:

- backend PHPUnit,
- PHPStan level 8,
- Composer audit,
- frontend Vitest,
- frontend security pack,
- TypeScript,
- ESLint and API wiring,
- MSW/API contracts,
- production frontend build,
- npm audit according to the approved severity policy,
- content/storage diagnostics,
- extension/static security pack,
- controlled test-artifact cleanup.

The runner must return a non-zero exit code when a required step fails. An optional step should be reported as `skipped` with a reason, not silently omitted.

### 4.3 CI gate

CI is independent evidence from a clean checkout. Minimum jobs:

| Job | Required evidence |
|---|---|
| Backend | Composer install from lockfile, PHPUnit, PHPStan L8, syntax, audit |
| Frontend | `npm ci`, type-check, lint, API barrel, Vitest, production build, audit |
| Integration | bootstrap, HTTP contract, auth/CSRF/RBAC, storage diagnostics |
| Security | SSRF, traversal/ZIP, CodePolicy, XSS/rendering, log sanitization, secret scan |
| Docs | links, front matter, code fences, and SK/EN parity for changed documents |
| Artifact | build, archive contents, SHA-256, and optional SBOM/signing evidence |

CI must not read a developer's local `.env`, reuse developer storage, or depend on a manually prepared file on a self-hosted runner.

### 4.4 Release acceptance

The release gate extends CI with:

- clean-clone first-run,
- HTTP smoke of the built artifact,
- upgrade test from a supported previous version,
- backup + restore on a separate tree,
- rollback or roll-forward scenario,
- verification that the artifact contains no `.env`, secrets, private logs, or test data,
- immutable commit/tag and checksum.

Detailed checklist: [BETA_INFRA.md](BETA_INFRA.md).

## 5. Backend tests

### 5.1 Unit tests

A unit test should verify one contract without production storage or network access. Preferred tools:

- a real temporary directory created by the test,
- filesystem adapter/fake,
- clock/UUID/random provider injected through DI,
- explicit HTTP client stub,
- small fixtures with clear ownership.

`vfsStream` can be useful, but must not hide real filesystem behavior such as rename, `fsync`, symlinks, permissions, or cross-device moves. Atomic writes and archive handling should also be tested on a real temporary filesystem.

### 5.2 Repository and storage tests

Every authoritative writer should test:

- creation of a new document,
- update with an expected revision,
- conflict with a stale revision,
- schema validation before writing,
- write-to-temp + rename,
- temporary-file cleanup after failure,
- preservation of the previous valid version,
- index rebuild from disk SSOT,
- unreadable or corrupted file behavior,
- parallel or simulated concurrent writers.

Indexes and caches are not tested as the only source of content. A test must be able to remove a derived layer and rebuild it from files.

### 5.3 HTTP integration tests

HTTP tests should bootstrap real routes and middleware while using isolated sessions and storage. For a mutating endpoint, verify at least:

| Scenario | Expected result |
|---|---|
| no session | `401` or an approved public contract |
| session without permission | `403` |
| permission without CSRF | `403`/canonical CSRF code |
| invalid payload | `422` |
| stale revision or lock conflict | `409` |
| valid mutation | 2xx + audit + consistent disk state |
| WAF block before routing | response may not use the JSON envelope |

Do not assert only on message text. Check status, content type, stable `code`, relevant headers, and storage state.

Response contract: [API_CONTRACT.md](../architecture/API_CONTRACT.md).

### 5.4 Test environment

`APP_ENV=testing` must be set before bootstrap. The suite should not automatically load a local production `.env`. Values required by tests should be created in the test bootstrap/fixture layer.

Before each HTTP test, reset or isolate:

- session,
- login/OTP/rate-limit state,
- fake clock,
- queue/outbox,
- firewall incident store,
- test settings repository,
- temporary storage root.

Historical regressions where failed login tests caused later `429` responses or a local demo flag changed OTP behavior belong in the permanent regression pack.

## 6. Frontend tests

### 6.1 Component and hook tests

Frontend tests should verify user behavior rather than React implementation details. Prefer:

- queries by role, label, and accessible name,
- `userEvent` instead of directly invoking handlers,
- loading/empty/error/success state coverage,
- keyboard flow and focus-return checks for dialogs,
- stable assertions against visible outcomes.

Brittle text snapshots or assertions on an exact internal render count are appropriate only when that is a real contract.

### 6.2 API and MSW

MSW handlers should match the documented API contract. Required mutation variants:

- success envelope,
- `401`,
- JSON `403`,
- plain-text/empty WAF `403`,
- `409` revision/lock conflict,
- `422` field errors,
- `429` with retry information,
- `500` without leaking an internal stack trace.

The frontend API client should inspect status and content type before parsing the body.

### 6.3 Production build

`npm test` is not enough. The gate should also run a production build and verify:

- Vite imports and lazy chunks,
- correct base path,
- absence of dev-only modules,
- source-map policy,
- asset manifest,
- no embedded secrets or private API URLs,
- compatibility with the frontend extension model.

Frontend plugin code discovered through `import.meta.glob` remains a build-time artifact. A backend plugin activation test must not falsely claim that a new React bundle was loaded at runtime without a rebuild/deploy step.

## 7. Security regression pack

A security test must protect a boundary, not only a class name. Required families:

| Area | Minimum scenarios |
|---|---|
| Auth | session fixation, logout, lockout, reset enumeration, 2FA replay |
| Authz | USER/EDITOR/ADMIN/SUPER_ADMIN, object/path access, queue identity |
| CSRF | missing, invalid, expired token; exempt routes only by allow-list |
| Filesystem | `..`, encoded traversal, absolute path, symlink, rename race |
| Upload/ZIP | size, MIME, content sniff, Zip-Slip, symlink, archive-bomb limits |
| SSRF | private/reserved IP, DNS rebinding, redirect revalidation, timeout |
| XSS/rendering | HTML/Markdown/SVG, dangerous URL schemes, stored content |
| Extensions | forbidden calls, manifest schema, disabled-after-import, rollback |
| Logging | CR/LF/ANSI/CSV injection, secret redaction, request correlation |
| Hybrid Engine | cache bypass, stale index, duplicate job, publish retry, locale isolation |
| AI/translation | prompt-injection boundary, schema tool call, authorization on Apply |

Static grep helpers are useful low-cost safeguards, but not the only evidence. Grep cannot reliably distinguish a safe wrapper, alias, dynamic call, or runtime redirect.

Security model: [SECURITY.md](SECURITY.md).

## 8. Hybrid Engine test matrix

Capabilities It.68–77 are added incrementally. Each should be tested with the feature **off** and **on**.

### 8.1 Index and cache

- the application works without Redis,
- a failed capability probe does not enable the Redis backend,
- a cache miss is not a content miss,
- a stale index is detected and rebuildable,
- invalidation after a write is idempotent,
- ETag/Last-Modified matches the content revision,
- cache keys include locale and relevant permission scope.

### 8.2 Git publishing and jobs

- local save succeeds even when an optional Git push fails,
- `stored`, `pending_publish`, `committed`, `pushed`, and `publish_failed` are not reported falsely,
- retries use an idempotency key,
- two workers do not create duplicate commits,
- a job carries the initiator's identity and permissions,
- dead-letter/failure state is visible and audited.

### 8.3 Media

- metadata remains flat-file SSOT,
- local and S3 drivers satisfy the same domain contract,
- an incomplete upload does not create a valid published record,
- a signed URL cannot bypass ACL,
- delete/restore handles both the physical object and metadata consistently.

### 8.4 Localization, translation, and AI

- locale fallback is deterministic,
- translation creates a draft rather than automatic publication,
- the diff is bound to the input revision,
- Apply rechecks permission and revision,
- untrusted content is not treated as a system instruction,
- tool calls pass JSON-schema/allow-list validation,
- the AI agent has no shell, generic filesystem, or implicit SUPER_ADMIN access.

## 9. Test data and isolation

### 9.1 Zero contact with production data

Tests must not read or write production:

- `data/settings.json`,
- user accounts,
- content and navigation,
- media,
- logs and audit,
- backup archives,
- developer tokens,
- real queue/outbox.

Recommended model:

```text
backend/storage-test/<unique-run-id>/
├── app/
├── data/
├── cache/
├── logs/
└── tmp/
```

Each run receives a unique root. Parallel CI jobs must not share one `settings.testing.json` or index.

### 9.2 Cleanup

The safest cleanup is deletion of the entire unique test root created by that run. Prefix heuristics such as `*@example.com` are suitable only as a transitional safeguard for historical shared storage.

Cleanup must:

- run in a `finally`/teardown phase,
- reject any path outside the test root,
- report what it removed,
- preserve a diagnostic artifact on failure according to CI policy,
- never default to production storage.

`content:diagnose --fix` repairs derived layers. It is not a universal production-data cleanup command after tests.

## 10. Flaky tests

A flaky test is a gate failure, not folklore fixed by clicking “Re-run” a third time. When a flake appears:

1. mark the candidate as unverified,
2. capture seed, runtime, timezone, locale, order, and logs,
3. reproduce with repeated or isolated runs,
4. fix global state, race, time, network, or brittle assertions,
5. add a regression test,
6. only then remove quarantine.

Automatic retry can help diagnostics, but it must not convert a red first run into green release evidence without a visible note.

### 10.1 HTTP integration test isolation (`Http/TestCase`)

PaginiumCMS HTTP controller tests boot a real Slim app against shared flat-file storage under `backend/storage/app/content/`. Without explicit hygiene, **order-dependent flakes** appear in full-suite runs even when isolated tests pass.

| Rule | Implementation | Incident |
|------|----------------|----------|
| Reset auth lockout state | `TestStorageCleaner::purgeLoginAttempts()` + `LoginAttemptTracker::clearAll()` in `setUp` | [ISS-073](../ISSUES.md#iss-073), [ISS-134](../ISSUES.md#iss-134) |
| Avoid shared client IP | Set synthetic `REMOTE_ADDR` on every `createJsonRequest()` (do not rely on default `unknown`) | [ISS-134](../ISSUES.md#iss-134) |
| Apply settings overrides after auth traffic | When a test mutates `settings.testing.json` and also calls register/login, write settings **after** the user session exists if middleware reads settings during auth | [ISS-134](../ISSUES.md#iss-134) |
| Do not call `SettingsRepository::reset()` in HTTP `setUp` | Nested `flock` via `DocumentValidator` during locked writes can deadlock the suite | [ISS-134](../ISSUES.md#iss-134) |
| Force demo/test env | `phpunit.xml` `DEMO_MODE=false force="true"`; sync `$_SERVER` in `Http/TestCase` | [ISS-125](../ISSUES.md#iss-125) |

When debugging a suspected flake, run the failing class **twice in one PHPUnit process** (default order) and capture the JSON error body on assertion failure.

```bash
./vendor/bin/phpunit --filter 'testRunForbiddenWhenDeployDisabled|testRunQueuesJobWhenEnabled' \
  backend/tests/Http/Controllers/Admin/SystemUpdateControllerTest.php
```

## 11. Dependency, SCA, and supply-chain checks

Minimum:

```bash
composer audit
cd frontend
npm audit --audit-level=high
```

The concrete severity policy must be versioned. When the project temporarily accepts an advisory, record:

- advisory ID,
- affected version and surface,
- reason for temporary acceptance,
- compensating control,
- owner and review date,
- fixed version or migration plan.

An `npm audit` exit code does not decide real exploitability by itself, but a SPA-only claim also does not automatically invalidate an open-redirect or client-side XSS finding. The decision should be documented in [ISSUES.md](../ISSUES.md) or the security review.

Release artifacts should be built from lockfiles. Adding SBOM and signing/provenance evidence is a recommended target.

## 12. Results, logs, and artifacts

A test report should include:

- commit SHA/tag,
- UTC timestamp,
- PHP/Node/npm/Composer versions,
- OS/container image,
- test-category name,
- pass/fail/error/skipped,
- duration,
- seed or shard,
- log/artifact reference,
- unambiguous final exit status.

Logs must not contain session cookies, CSRF tokens, passwords, `APP_KEY`, OAuth secrets, SMTP credentials, or full sensitive payloads. Sanitize logs before attaching them to a public issue.

Recommended machine-readable summary:

```json
{
  "commit": "<sha>",
  "startedAt": "2026-08-02T12:00:00Z",
  "environment": {"php": "<version>", "node": "<version>"},
  "checks": [
    {"name": "phpunit", "status": "passed", "durationSeconds": 82},
    {"name": "content-diagnose", "status": "passed", "durationSeconds": 3}
  ],
  "status": "passed"
}
```

## 13. Manual and smoke tests

### 13.1 Critical admin smoke

- login and logout,
- 2FA according to profile,
- draft creation,
- editing and save,
- conflict from a second session,
- publish according to the implemented lifecycle,
- media upload,
- RBAC/Path ACL deny,
- audit and log record,
- backup and restore on a separate tree.

### 13.2 Postman/Newman

The collection in `docs/api/PaginiumCMS.postman_collection.json` is a supplemental smoke subset:

```bash
npx newman run docs/api/PaginiumCMS.postman_collection.json \
  --env-var baseUrl=http://127.0.0.1:8080
```

It is not a complete OpenAPI specification or a replacement for HTTP contract tests. Do not store secrets directly in the collection.

### 13.3 Production smoke

Run only safe post-deploy verification in production:

```bash
curl --fail --silent https://example.test/api/health
php backend/bin/console content:diagnose
php backend/bin/console content:locale-migrate inventory
```

Optional pre-migration operator check (It.73): `content:locale-migrate dry-run --default-locale=sk` before `run --yes`. Rollback: `content:locale-migrate rollback --migration-id=<id> --yes`.

Run the full PHPUnit/Vitest suite in CI or a disposable environment, not against live production storage. A production server is a very expensive test fixture.

## 14. Definition of Done for a change

A change is complete when:

- a test protects the new or repaired contract,
- negative and permission paths are covered where relevant,
- tests use isolated data,
- the fast gate is green,
- the required full/CI gate is green,
- documentation and API contracts are updated,
- a new incident has a regression test and a link in `ISSUES.md`,
- a skip/quarantine has a reason, owner, and expiry,
- a release-impacting change has upgrade/rollback evidence.
